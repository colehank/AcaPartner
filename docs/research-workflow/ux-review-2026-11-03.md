# 全流程 UX 复盘：从 idea 或进行中的研究进入

日期：2026-11-03。范围：当前科研工作台全部主要入口与接续路径，以 `frontend/src/workbench/main.tsx` 为稳定目标。状态：评审与调整建议，尚未实施交互重构。

Method: dual-agent (A: ux_design_review · B: ux_evidence_review)

用户明确的起点是带着一个 idea 开始，或带着已经做了一半的研究继续。两种协作均保留：随时讨论，也能把完整工作交出去。研究问题可以并列、递归，各有独立 AEC；自由记录与不完整结构均可存在，不指定唯一主 Q。

## 核心判断

现有三栏外壳、内容编辑、准确版本和候选审阅有可复用基础。当前流程主要按后端能力分别设入口，研究者因此需要先理解问题提案、普通委托、Q 工作、登记材料与执行配置，再选择如何继续。功能的技术闭环尚未形成清楚的使用闭环。

前几轮验证证明了保存、版本检查、候选生成和采用能够完成，没有证明初次使用者能自行找到下一步。本次是两路独立的设计者走查，不是真实用户可用性研究；启发式评分不能当作用户成功率。

## 两种入口的实际体验

| 起点 | 已验证的路线 | 主要断点 |
| --- | --- | --- |
| 一个 idea | 创建项目只填名称；空概览展示背景、问题、交付；右侧“讨论”输入后点箭头，转入中央问题探索表单；核对输入后才展示路线、时限与开始动作 | 对话外观没有给出对话反馈；用户需要自行理解从讨论到表单的转换，并选择“梳理问题”还是“编写委托” |
| 进行中的研究 | 文件树可打开原生实验笔记和 Python 工作副本；Q 页可看当前认识与相关工作；登记报告可进入委托并返回候选 | 原生笔记和脚本可见，却没有直接进入 Agent 材料的路径；从当前笔记点“编写委托”也不会带入其正文；项目概览没有接手整个已有研究的入口 |

不能把“没有材料也能探索”误判成“必须先填完整 QAEC”。技术上并无此要求；问题在于空态和入口层级仍容易让人以为需要先整理好背景与 Q。

## 五项优先问题

### P1：项目没有接手用户当前状态

空项目和进行中项目共用近似的概览与搭档介绍。用户需要自己寻找可继续的工作，待处理候选主要藏在“委托”列表中。

调整：空项目围绕写下想法、带入已有研究；已有项目优先显示当前认识、进行中的工作、需要本人查看的内容，以及少量有理由的下一步。允许直接进入对象工作，不增加必填研究向导。建议用 `impeccable shape / onboard` 整理此入口。

### P1：可见内容与 Agent 实际输入不一致

实测 `notes/实验记录.md` 正文可读写，但研究材料页和工作材料抽屉只列登记报告。从笔记打开普通委托，目的同时提及笔记与报告，解析也只纳入报告。右栏的当前文件标题没有表达“只是位置”与“正文已纳入”之间的区别。

调整：统一当前内容、选区与保存材料的上下文表达；对支持的类型直接取得准确版本，显示实际采用范围，可检查、可移除；不支持的格式给出具体状态与可执行替代路径。原生文件输入适配是后台缺口，改标签不能解决。复用现有文件读取、版本和来源机制，不新增另一套项目库。建议用 `impeccable shape / clarify` 对齐。

### P1：用户被要求选择内部工作类型并管理执行细节

“讨论”的箭头打开问题提案；“编写委托”创建报告或笔记；Q 的“推进这个问题”创建 AEC 修改候选。一般委托还要求同时处理目的、产出类型、来源、路线、调用次数、秒数与授权确认。

调整：以同一个项目搭档为主入口，持续保留当前研究上下文。讨论与交出工作共同围绕研究意图，由系统整理范围、来源及产物，呈现简短、可调整的工作说明。已有授权内的常规工作使用可解释默认值；高级路线和预算折叠。范围扩大或执行方式改变时再提出具体决定。QAEC 的作用是组织研究认识，用户不必每次先选 A/E/C。建议用 `impeccable distill / clarify` 降低外在负担。

### P1：执行结束、候选处理与恢复缺少连贯的交接

同一任务在右栏为 `generated` / `failed`，中央为“候选已保存／执行未完成”。任务数量没有表明哪些需要用户处理。独立失败场景中，用户需展开记录、打开原始任务详情，再自行回树寻找 Q；没有直接继续当前问题或判断如何重试的入口。

调整：统一为有用户含义的状态，如进行中、需要查看、已更新、需要处理。完成后先说明做了什么、改变了什么、依据和限制；给出查看变化、调整或继续工作的动作。采用后回到更新对象并说明本次变化。失败时保留输入和记录，提供与真实状态相符的核对、重试或继续动作；不得用一个通用“重试”盲目重复调用或清空预算。建议用 `impeccable harden / clarify` 完成交接。

### P2：研究、材料与交付仍是可打开的页面，尚未形成清楚的接续

真实 DOCX 能渲染，默认论文源稿选择也区分 DOCX 与 LaTeX；脚本保存明确不执行。但从研究判断到稿件表达、从脚本到计算结果的后续动作尚未贯通。未选源时标签却已叫“论文.docx”；智能体配置页面保存的是待接入配置，不会建立执行连接。

调整：按实际能力说明下一步。论文保留为项目默认交付，打开、导入与编辑沿现有适配；研究结果进入写作的来源与局部修改属于后续独立能力。脚本可编辑和脚本可执行分别表达。设置页明确哪些服务已可用、哪些仅为记录，并给出真实接入路径。建议用 `impeccable clarify / onboard` 清楚组织边界。

## 建议的统一工作主线

两种起点进入同一个项目工作台：理解当前研究 → 提出有理由的下一步 → 讨论或交出一项工作 → 查看结果与变化 → 使用、调整或保留 → 回到更新的研究继续。

“理解当前研究”是搭档整理给用户检查的工作，不是新增一份必须填写的表单。已有研究不必先重排目录或填写 QAEC；未归类的材料可以保留。提案采用、实际计算与稿件写入继续遵守各自的来源、范围和版本规则。

- idea 入口：用户写下想法，搭档先给出简短理解和影响方向的关键澄清；再提出可研究方向或下一项有用工作。形成 Q 是可选择的研究动作，不是开始交流的技术门槛。
- 已有研究入口：用户带入现有资料并说明目前做到哪里、卡在哪里；搭档先说明实际读了哪些资料、已有认识和未知，再给出可修改的项目理解与下一步建议。自动读取与导入只在实际支持和授权范围内进行。
- 左侧继续定位同一项目的研究、材料、笔记和交付，文件与研究视角不另存两份内容。
- 中央继续阅读和编辑真实对象；核对候选时在对象上下文中看变化，避免流程被多个表单标签拆散。
- 右侧成为持续的项目搭档，讨论、工作进展与返回结果共享上下文；不是用聊天外观跳转到不同业务表单。
- 底栏维持既定服务／地址／用量与设置布局；科研状态和需要用户处理的内容放在研究与工作区域。

下一轮优先接通“带入研究—理解现状—继续工作”的主线，然后扩展多阶段 cycle。保留已有队列、固定来源、草稿与版本保护，不整体重写 Harness。

## 启发式评分

Assessment A 独立评分，B 提供真实行为与源码佐证。分数为主观评审，全部十项适用于 Operate/Read，总分 **23/40**。

| 项目 | 分数 | 关键依据 |
| --- | ---: | --- |
| 系统状态可见性 | 3 | 草稿与保存版明确；任务状态和待审数量不统一 |
| 与研究者语言匹配 | 2 | 科研词义正确；工作类型与文件／登记对象区别需要学习 |
| 用户控制与自由 | 3 | 能取消、手改与部分选择；有版本保护 |
| 一致性 | 2 | 外壳统一，三种工作入口与表单模式不同 |
| 错误预防 | 3 | 固定来源、草稿保护和明确采用可复用 |
| 识别优于记忆 | 2 | 能定位对象，但需要记住哪些内容可进入工作 |
| 使用效率 | 2 | 有搜索和比较，重复配置与跳转增加成本 |
| 美观与简约 | 3 | 阅读秩序较好，一般委托的密度与周围不同 |
| 故障恢复 | 2 | 有保存与请求保护，失败页的下一动作不足 |
| 即时帮助 | 1 | 有边界说明，缺少当下能做什么的帮助 |

认知负担八项检查：idea 路线失败 2/8（起步层级、澄清与回答的阅读往返）；进行中的研究进入一般委托失败 5/8（信息分块、层级、同时决策、选项、跨页记忆）。这不是研究复杂度本身过高，也不意味着应限制问题树节点或强制唯一主 Q。

## 应保留的基础与小问题

应保留：三栏与稳定对象导航；连续 QAEC 阅读；研究判断与任务完成的区分；固定来源和逐项比较、编辑及采用；冲突与草稿保护。

三类使用者的风险：首次进入者可能把讨论理解为聊天后又遇到表单；已有半成品的人会以为当前文件已被读取，却仍需搬运上下文；熟练使用者需要在相近入口之间切换并重复配置。情绪低谷集中在输入想法后再配置，以及明明看得到文件却无法交给搭档；候选比较是已存在的体验高点，但处理后的下一步仍不突出。

小问题：Cmd+K 和鼠标打开搜索后，焦点实际落在关闭按钮，需 Tab 后才能输入；右栏仍有原始英文任务状态；源稿未选定却出现 DOCX 文件名；全局页面中右栏显示全局页名但仍关联原项目，归属容易含混；探索提案上方澄清与底部补充输入相隔较远。搜索焦点适合后续 `impeccable harden` 一并处理。

## 证据与边界

A、B 使用各自新建的 Chrome 标签独立走查；A 完成前 B 的扫描结果未进入综合上下文。实测覆盖主页／创建对话框、两种起点、探索预览、提案选择与标题刷新恢复、笔记、脚本、普通委托来源解析、Q 相关工作、AEC 比较与固定来源、真实 DOCX 阅读、失败页、配置和搜索。没有发起真实模型调用、保存或采用候选、上传或编辑用户文稿。

候选由真实 Runtime 与模型替身在独立工作区生成；失败任务为预置状态。不能据此声称本次验证了模型质量、真实超时、采用事务、DOCX 往返、LaTeX 编译、脚本执行、SSH 或辅助技术完整流程。过去自动化测试只作为已有实现佐证，没有在本次重跑。

CLI detector 对 `frontend/src/workbench` 返回 `[]`、退出码 0，共 0 条，故无规则名、定位或假阳性；未返回逐文件覆盖，目录外的普通委托、任务详情与上游编辑器未被该扫描证明。零命中不能说明用户流程顺畅或可访问性达标。

浏览器 API 只允许只读 evaluate，无法注入 overlay；本次没有页内 overlay、脚本注入或检测 console 结果，以真实 DOM／截图观察加 CLI 为证。没有启动 overlay 服务。两个评审标签已关闭；隔离审查服务在报告前停止，用户预览服务保持。归档遵循已有文档位置约定，未重建用户已删除的 `.impeccable`。

## 待确定的交互默认值

1. 已有研究接入后，默认先展示搭档整理的研究现状与下一步，还是先进入原文件目录？建议前者，同时保留直接打开文件的入口。
2. 日常协作以同一个输入框理解讨论与具体工作，还是要求用户主动切换讨论／交出工作模式？建议同一主输入，同时让工作范围、运行和待审结果保持可见。
